### 🔴 A6：本轮发现一个真问题 —— **事件消息去重失效**

**证据**（同一条 CLICK 事件、`CreateTime` 完全相同，连发两次，模拟微信重试）：

```
2026-09-22T20:44:07.267  c.w.r.m.WxMessageLogMapper.insertIgnore : <==  Updates: 1
2026-09-22T20:44:07.280  c.w.r.m.WxMessageLogMapper.insertIgnore : <==  Updates: 1
                                          ↑ 同一事件写了两次
```

同时日志里事件消息的参数一直是 `null`：

```
==> Parameters: null, oUserOpenid(String), gh_abc123(String), event(String), CLICK(String), null
                 ↑ msg_id 为 null                                       ↑ content 为 null
```

**根因**：微信的**事件消息不带 `MsgId`**（`CLICK` / `subscribe` / `unsubscribe` 都没有），
所以 `msg_id` 落成 `NULL`。而 MySQL 的**唯一索引对 `NULL` 不比较** —— 多个 NULL 不算重复，
于是 `INSERT IGNORE` 每次都能插进去，**去重形同失效**。

**影响**：微信在网络抖动/超时时会**重试推送**（最多 3 次）→ 消息记录里出现重复行 →
数据看板统计偏高。这是开发期的隐性缺陷，联调时就会真实发生。

**建议改法**（对应 `docs/P0-遗留问题-改法问答.md` 的遗留 #2）：

1. 给 `wx_message_log` 加一列 `dedup_key CHAR(64) NOT NULL`，唯一索引建在它上面；
2. 取值规则：
   - 有 `MsgId` → `msg:<MsgId>`
   - 事件消息 → `evt:<FromUserName>:<Event>:<EventKey>:<CreateTime>`
3. 微信重试时这几项**完全相同**，所以能挡住；而正常的新事件 `CreateTime` 必然不同，不会被误杀。

> ⚠️ 这涉及 **DDL（加列 + 建唯一索引 + 回填历史数据）**，按约定**等你确认后我再动**。
> 是否在联调前修，你定：**修了更干净**；不修也能先联调，只是记录里会出现重复。

## 排错表

| 现象 | 大概率原因 | 怎么查 |
|---|---|---|
| C1 提交报参数错误 | Token 不一致 / URL 少 `/wx` / 隧道未连 | 先 `curl -s -o /dev/null -w '%{http_code}' https://<隧道域名>/wx` |
| 提交成功但发消息无反应 | Mac 睡眠、隧道断开 | 重起隧道；看终端2 是否还活着 |
| 收到「该公众号暂时无法提供服务」 | 后端 5xx（MySQL 没起 / DB 密码错） | 看 B3 终端日志；`lsof -nP -iTCP:3326 -sTCP:LISTEN` |
| 忽然全部失效 | 免费版隧道域名变了 | 回 C1 改 URL 重新提交 |
| 菜单接口报 `40164` | 出口 IP 不在白名单 / IP 变了 | `curl -4 ifconfig.me`，回后台重加 |
| 点了菜单没反应 | 菜单用后台图形界面配的（key 对不上） | 见方案文档 §四；改用 `/api/menu` 下发 |
| 端口 18080 被占 | 上次后端没退干净 | `lsof -nP -iTCP:18080 -sTCP:LISTEN` → `kill` |
