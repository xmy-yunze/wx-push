# 自定义菜单 · 方案

> 交付时间：2026-09-22
> 配套文档：`docs/自定义菜单-检测清单.md`（检测清单）、`docs/admin-接口契约.md`（接口约定）
> 定位：**用户端最后一块功能**。菜单是未认证订阅号「能主动呈现给关注者」的唯一 UI，
> 做完它，本地框架的功能面就闭环了。

## 一、为什么菜单是「小而完整」的最后一块

个人未认证订阅号的权限是**永久封顶**的，能力只有四项：

| 能力 | 状态 | 说明 |
|---|---|---|
| 服务器配置（收消息） | ✅ 能做 | P0 已完成 |
| 被动回复 | ✅ 能做 | P0 已完成 |
| **自定义菜单** | ✅ 能做 | **本次** |
| 客服消息 / 群发 / 素材 / 用户管理 / 网页授权 / 模板消息 / 支付 | ❌ 不可用 | 认证后才开放 |

其中**只有自定义菜单**是「我们主动推给微信、让用户看得见」的东西。
其余三项都是「用户先来找我们、我们被动响应」。所以菜单补上之后，
「用户能看到什么 → 用户点了什么 → 我们回什么」这条完整链路才真正合上。

### 1.1 一个必须先讲清的限制：菜单不能跳外链

未认证订阅号的 `view` 型菜单（点击打开网页）**只能指向 `mp.weixin.qq.com` 域名下的页面**，
指向其它域名（包括我们自己的服务器）会报错：

```
errcode 45058 —— 未认证订阅号不支持跳转外部链接
```

微信的用意是防止未认证主体用菜单导流到站外。对我们的影响：

- **不能**用菜单把用户导到自己的 H5 页面（`h5/` 目录因此一直定位待定，见技术方案 2.1）
- **可以**用 `click` 型菜单——点击后微信把一个 `CLICK` 事件推给我们的 `/wx` 接口，
  我们被动回复一条文本。用户看到的是「点菜单 → 收到回复」，体验完整，且**完全不涉及外链**

**结论：本项目的菜单全部用 `click` 型。** 这不是妥协，而是未认证号下唯一能做出完整体验的形态。
`view` 型能力保留在代码里（`ViewButton` + 域名白名单校验），将来认证了直接可用。

## 二、设计模式落点（本项目核心，与技术方案 P1 第 8 项对齐）

这一块是**设计模式练习密度最高**的一次，一次落了 6 种。方案文档第五节的模式表里，
自定义菜单一行对应「组合 + 建造者」，实际做下来另外 4 种也自然长了出来：

| 模式 | 落地类 | 为什么这里必须用它 |
|---|---|---|
| **组合（Composite）** | `MenuButton`（组件）/ `SubMenu`（容器）/ `ClickButton`、`ViewButton`（叶子） | 菜单是天然的两层树。用组合后，**校验、序列化、递归逻辑只写一遍**，叶子与容器对上层是同一个接口 |
| **建造者（Builder）** | `MenuBuilder` + `MenuCatalog` | 菜单嵌套两三层，直接 `new` 会形成「一大坨括号」。建造者让菜单定义读起来就是它本来的样子 |
| **适配器（Adapter）** | `WxApiClient` | 微信 4 个接口（token/menu-create/menu-get/menu-delete）入参出参风格不一，适配器统一成「传业务参数、拿业务结果、异常带人话」 |
| **单例 + 双检锁** | `AccessTokenManager` | 见第三节，这是**本次最关键的一处并发设计** |
| **门面（Facade）** | `MenuService` | 对 Controller 只暴露 `currentMenu / publish / clear` 三个动作，隐藏「解析→渲染→调接口→token 重试」的全部复杂度 |
| **策略（隐式）** | `MenuButton.isContainer()` + 多态 `toMap()` | 遍历菜单树时**不需要 `instanceof`**，容器与叶子各自实现自己的序列化 |

> ⚠️ 这一块刻意**没有**做「模板方法」——菜单没有「固定流程 + 可变步骤」的特征，
> 硬套只会变形。模式服务结构，不是结构服务模式。

## 三、核心难点：access_token 单例与双检锁

### 3.1 微信的规则（这是设计的出发点）

- `access_token` 是**调用一切主动接口的凭证**（菜单增删查都要带它）
- 它是**全局唯一**的：**每次调用 `/token` 获取新 token，都会让上一个立即失效**
- 默认有效期 **7200 秒**（2 小时）
- 高频获取会被限流

这三条合起来意味着一个经典陷阱：

> 如果两个线程同时发现「token 过期了」，各自去拿一次新 token，
> 后拿的那个会让先拿的那个**当场作废**——于是先拿的线程拿着废 token 调菜单接口，
> 微信返回 `40001（invalid credential）`。表现为**偶发、难复现、并发一上来就报错**。

### 3.2 解法：单例 + 双检锁 + 提前刷新

```
AccessTokenManager（进程内单例）
  volatile TokenHolder holder          ← volatile 保证可见性
  ├─ get()                             ← 快路径，无锁读
  │    ① 读 holder，若未过期 → 直接返回（绝大多数请求走这里，零锁开销）
  │    ② 过期 → 进 synchronized 块
  ├─ fetch()（synchronized）           ← 慢路径，锁内完成
  │    ③ 双检：再查一次 holder 有没有被别人刷过 → 刷过就直接用
  │    ④ 都没刷 → 真的发网络请求拿新 token，写回 holder
  └─ invalidate()                      ← 遇 40001/42001 时丢弃缓存
```

三个关键决策：

| 决策 | 取值 | 理由 |
|---|---|---|
| **提前刷新窗口** | 提前 **5 分钟**（`REFRESH_AHEAD`） | 不留窗口期。若卡在刚好过期的瞬间，业务请求会撞上「token 刚失效」，白跑一次 |
| **网络请求放在锁内** | 是 | 宁可锁持有久一点，也不能让两个请求同时打到 `/token`（那正是让 token 互相作废的根因） |
| **失败即丢缓存** | `invalidate()` + 重试一次 | 若本地认为 token 有效、但微信已经作废（比如别处也拿了 token），重试一次即可自愈 |

> **为什么不引 Redis？** 单机部署下进程内单例已经正确且最快。
> 将来多实例才需要把 token 挪到 Redis——**只改 `AccessTokenManager` 一个类的存取实现**，
> 上层调用完全不动。这就是「单例收口」的收益。

### 3.3 重试策略落在 `MenuService.withTokenRetry`

`WxApiClient` 只管「调接口、出错抛 `WxApiException`」；
「token 失效 → 丢缓存 → 重试一次」这个策略放在 `MenuService`：

```java
// 伪代码
try {
    return action.call();
} catch (WxApiException e) {
    if (e.isTokenInvalid()) {        // 40001 / 42001
        accessTokenManager.invalidate();
        return action.call();        // 只重试一次，避免死循环
    }
    throw e;
}
```

**分层理由**：`WxApiClient` 是「微信协议适配」，不该懂业务重试策略；
`MenuService` 是「菜单业务门面」，由它决定「token 失效可以重试」。
**这也是适配器模式的价值——换协议不改策略。**

## 四、菜单数据模型（组合模式）

```
MenuTree（根，一级 ≤ 3 个）
 └─ MenuButton（抽象组件：name、校验、toMap、isContainer）
     ├─ ClickButton（叶子，type=click，key ≤ 128 字节）
     ├─ ViewButton （叶子，type=view，url 必须 mp.weixin.qq.com 域名下）
     └─ SubMenu    （容器，二级 ≤ 5 个，不可再嵌套）
```

### 4.1 校验规则（全部在本地拦掉，不让微信报错）

微信对菜单的约束是硬性的，超了会返回含义模糊的错误码（如 `40054`）。
**本地先校验、给出人话提示**，比让运营者对着微信错误码猜好得多：

| 规则 | 违反时提示 |
|---|---|
| 一级菜单 ≤ 3 个 | 「一级菜单有 N 个，微信最多允许 3 个」 |
| 二级菜单 ≤ 5 个 | 「『xxx』的子菜单有 N 个，微信最多允许 5 个」 |
| 菜单名一级 ≤ 8 字符 / 二级 ≤ 16 字符（**中文按 2 计**） | 「菜单名『xxx』过长」 |
| 只支持两级（三级会被拒） | 「菜单只支持两级，『xxx』不能再嵌套」 |
| 子菜单不得为空 | 「菜单『xxx』的子菜单不能为空」 |
| 仅支持 `click` 与 `view` | 「不支持的菜单类型：xxx，仅支持 click 与 view」 |
| `view` 的 url 必须 `mp.weixin.qq.com` 域名下 | 「未认证订阅号不支持跳转外部链接（45058）」 |

> 📌 **`name` 长度按「中文算 2 字符」**：这是最容易漏的一条。
> 「关于我」看着 3 个字，微信按 6 字符算。用 `String.length()` 判断会被微信拒。

### 4.2 `MenuCatalog` —— 菜单与文案的唯一维护点

`click` 型菜单的 `key` 是我们自己编的字符串（如 `MENU_ABOUT`），微信只负责**原样带回来**。
所以「菜单上写着『怎么用』」和「点了以后回复什么」是**强绑定**的一对信息。

如果菜单定义在 A 处、回复文案写在 B 处，改菜单时极易忘记同步文案——
**表现为「用户点了菜单没反应」而代码看起来毫无问题**。

因此 `MenuCatalog` 把这两件事放在同一个类：

```java
// KEY_* 常量被菜单构造与文案表共用 → 拼错编译期就报错
public static final String KEY_ABOUT = "MENU_ABOUT";
...
public static MenuTree defaultMenu() {
    return MenuBuilder.create()
            .click("关于我", KEY_ABOUT)
            .sub("更多", sub -> sub
                    .click("怎么用", KEY_HOWTO)
                    .click("联系我", KEY_CONTACT))
            .click("当前进度", KEY_PROGRESS)
            .build();
}
public static Optional<String> replyForClick(String key) { ... }
```

默认菜单的三个一级项**刻意覆盖两种形态**：两个直接可点的叶子 + 一个带二级的容器，
这样组合模式的两条路径都能被真实验证到（而不只是单测里覆盖）。

> ⚠️ **未知 key 返回 `Optional.empty()`，不报错**。
> 因为菜单可能被运营者在微信公众平台手工改过——未知 key 是正常情况，
> `EventMessageHandler` 据此决定「不回复」，而不是抛异常。

## 五、接口契约（供前端对齐）

三个端点都在 `/api/**` 下，被 `LoginInterceptor` 自动保护，**不需要额外写鉴权**。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/menu` | 查线上真实菜单（微信原始结构 `{"menu":{...}}`） |
| `POST` | `/api/menu?dryRun=false` | 发布菜单（**覆盖**线上现有菜单） |
| `POST` | `/api/menu?dryRun=true` | **干跑**：只校验 + 回显报文，不调微信 |
| `DELETE` | `/api/menu` | 清空线上菜单（恢复默认状态） |

`POST` 返回：

```json
{
  "code": 0,
  "data": {
    "published": false,          // dryRun 为 false；真发布为 true
    "payloadJson": "{\"button\":[...]}"   // 实际发送/将要发送给微信的报文
  }
}
```

### 5.1 干跑（`dryRun`）为什么重要

> **这是本地开发的救命功能。**

未认证号调微信接口有 **IP 白名单**要求：调接口的机器公网出口 IP 必须写进公众平台后台，
否则微信返回 `40164（invalid ip, not in whitelist）`。
而家庭/热点网络 IP 是**动态**的，改一次要登录公众平台后台，很麻烦。

`dryRun=true` 时**完全不调微信**，只做「解析 → 校验 → 渲染报文」，
所以**没有 IP 白名单也能验证菜单结构是否正确**。前端 MenuView 默认就用干跑预览。

### 5.2 微信 API 错误码 → 人话提示

`WxApiClient` 内置错误码映射表（`HINTS`），异常信息形如
「人话提示（微信返回 errcode：errmsg）」：

| errcode | 含义 | 我们给运营者的提示 |
|---|---|---|
| 40013 | invalid appid | AppID 配置错误 |
| 40054 | invalid button | 菜单结构不合法（本地已尽量拦掉） |
| 40125 | invalid appsecret | AppSecret 配置错误 |
| **40164** | invalid ip | **公网出口 IP 未加入白名单** |
| 42001 | access_token expired | token 过期（会自动重试一次） |
| 45058 | 不支持跳转外部链接 | 未认证订阅号 `view` url 只能指 mp.weixin.qq.com |

`WxApiException` 经 `GlobalExceptionHandler` 统一转成 **HTTP 502**，
原样透传人话提示（不吞成「系统错误」）。

## 六、⚠️ Spring Boot 4.0.7 两个坑（血泪，务必先读）

### 坑 1：Jackson 3 换了包名

Boot 4 内置 **Jackson 3**，包名从 `com.fasterxml.jackson.*` 改为 `tools.jackson.*`：

| 旧（Jackson 2） | 新（Jackson 3） |
|---|---|
| `com.fasterxml.jackson.databind.ObjectMapper` | `tools.jackson.databind.ObjectMapper` |
| `com.fasterxml.jackson.databind.JsonNode` | `tools.jackson.databind.JsonNode` |
| `com.fasterxml.jackson.core.JsonProcessingException` | `tools.jackson.core.JacksonException` |

**编译期报错**（`package com.fasterxml.jackson does not exist`），不难查，但 IDE 自动导入
有可能给你导回旧包——**改完务必 `./gradlew compileJava` 复核**。

### 坑 2：`spring-boot-starter-webmvc` **不含** `RestClient`

Boot 4 把 Web 拆成了细粒度 starter。`spring-boot-starter-webmvc` 只给 MVC，
`RestClient.Builder` 的自动装配在**另一个** starter 里：

```groovy
// build.gradle —— 少了这一行，应用启动直接失败
implementation 'org.springframework.boot:spring-boot-starter-restclient'
```

**故障现象**：`No qualifying bean of type 'org.springframework.web.client.RestClient$Builder'`

> 🔥 **这个坑最阴险的地方**：**单测会全绿**。
> 因为单测里我们是手动 `RestClient.builder()` 构造 `WxApiClient`，
> 根本没走 Spring 容器装配。**只有真正启动应用时才炸**。
>
> **教训：单测全绿 ≠ 应用能启动。交付前必须真起一次后端。**
> （本次已实测：`--args='--server.port=18080 --server.address=127.0.0.1'` 启动成功。）

## 八、不属于本次范围（明确划清）

- **菜单落库**：不做。真相源（Source of Truth）在**微信服务器**——`GET /api/menu` 随时能拉回
  线上真实菜单，本地再存一份只会产生「本地与线上不一致」的坑。本地只缓存 token（内存）。
- **个性化菜单**：不做（认证号能力）。
- **`view` 型菜单实跳**：代码支持，但未认证号跳外链必报 45058，**线上不会配**。
- **定时刷新 token 的后台线程**：不做。用**惰性刷新 + 提前 5 分钟窗口**已足够，
  引入定时器反而多一个「进程活着但线程挂了」的故障面。
