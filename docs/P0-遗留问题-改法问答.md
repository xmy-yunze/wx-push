## 题 1 · `[Fatal Error]` 那行裸输出是谁打的？

### 现象

冒烟脚本跑到 `[7] 畸形报文` 时，stderr 里会出现这样一行（**每轮一次**）：

```
[Fatal Error] :1:1: 前言中不允许有内容。
```

它没有时间戳、没有日志级别、没有线程名 —— 显然是**绕过了 logback**。

### 答案

**来源：`javax.xml.parsers.DocumentBuilder` 的默认 `ErrorHandler`。**

`DocumentBuilderFactory.newDocumentBuilder()` 得到的 `DocumentBuilder`，如果你**不调用 `setErrorHandler()`**，JDK 会挂上一个内置默认实现。这个实现的 `fatalError()` 行为是：

> **先把错误直接打印到 `System.err`，然后才抛出 `SAXParseException`。**

**为什么绕过日志框架**：`System.err` 是**进程的标准错误流**，logback 的 appender 只接管「通过 logback API 输出」的内容。任何第三方库直接写 `System.err`，都会绕过你所有的日志格式、脱敏规则、采集配置。

**为什么功能仍然是对的**：因为默认实现**同时也抛异常** —— 你的 `catch (Exception e)` 捕获后转成 `IllegalArgumentException`，Controller 返回 200 + 空体。所以问题只是「多打印了一行裸文本」，逻辑没坏。

### 改法

在 `WxXmlParser.parse()` 里，拿到 builder 之后立刻挂自定义 `ErrorHandler`：

```java
DocumentBuilder builder = factory.newDocumentBuilder();

// 不挂自定义 handler 时，JDK 默认实现会先把错误打到 System.err（绕过 logback），再抛异常。
// 这里接管掉，改为「只抛不打印」——行为完全一致，只是不再污染标准错误流。
builder.setErrorHandler(new ErrorHandler() {
    @Override
    public void warning(SAXParseException e) {
        // 警告不影响报文语义，忽略
    }

    @Override
    public void error(SAXParseException e) throws SAXException {
        throw e;
    }

    @Override
    public void fatalError(SAXParseException e) throws SAXException {
        throw e;   // 关键：默认实现会在这里打印，我们只抛
    }
});
```

**行为不变的保证**：默认实现在 `fatalError` 里**也是抛异常**，所以上层 `catch` 到的异常类型与 message 完全一致 —— **唯一的变化是那行打印消失**。

> 备选做法：`factory.setFeature("http://apache.org/xml/features/continue-after-fatal-error", false)` 之类的开关都**不能**抑制打印，因为打印发生在 handler 层。必须换 handler。
> 另一个更省事的写法是直接 `builder.setErrorHandler(null)` —— 但这会让**解析错误被静默吞掉**，畸形报文不再抛异常，反而更糟。不要这么做。

### 验证方式

```bash
./gradlew bootRun                       # 终端 1
./scripts/smoke-test.sh wxToken123 8080 # 终端 2
```

| 期望 | 说明 |
|---|---|
| stderr 里**不再出现** `[Fatal Error]` | 核心断言 |
| 冒烟脚本仍是 **11 项全过** | 行为未变 |
| 日志里仍有 `微信报文解析失败：解析微信 XML 报文失败：前言中不允许有内容。` | 说明异常路径仍正常工作，只是改走 logback 了 |
| `[7] 畸形报文 → 200` 仍通过 | 契约未变 |

## 题 2 · 库写了 `COLLATE general_ci`，为什么表变成 `0900_ai_ci`？

### 现象

```sql
CREATE DATABASE IF NOT EXISTS wx_push
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_general_ci;      -- ← 库：显式写了 general_ci

CREATE TABLE IF NOT EXISTS wx_message_log (
    ...
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4;         -- ← 表：只写了 CHARSET，没写 COLLATE
```

建成后实测：

| 层级 | 字符集 | 排序规则 |
|---|---|---|
| 库 `wx_push` | utf8mb4 | `utf8mb4_general_ci` |
| 表 `wx_message_log` | utf8mb4 | **`utf8mb4_0900_ai_ci`** ← 没跟随库 |

### 答案

**因为 `DEFAULT CHARSET` 不带 `COLLATE` 时，排序规则取的是「该字符集的固有默认」，而不是「库的排序规则」。**

MySQL 的字符集/排序规则是**三级概念**：

```
服务器默认  →  库默认  →  表默认
```

但继承规则有个容易踩的反直觉点：

| DDL 写法 | 结果 |
|---|---|
| 什么都不写 | 字符集 + 排序规则都继承**库** |
| 只写 `CHARACTER SET = X` | 字符集 = X；**排序规则 = X 的固有默认**（不是库的） |
| 同时写 `CHARACTER SET = X COLLATE = Y` | 两者都用你指定的 |

**实测证据（只读查询确认）**：

```sql
SELECT CHARACTER_SET_NAME, DEFAULT_COLLATE_NAME
FROM information_schema.CHARACTER_SETS
WHERE CHARACTER_SET_NAME = 'utf8mb4';
```

结果：

| 字符集 | 默认排序规则 |
|---|---|
| utf8mb4 | `utf8mb4_0900_ai_ci` |

而本机 `collation_server` 也是 `utf8mb4_0900_ai_ci`。所以表「回落到」了 `0900_ai_ci`。

**结论**：这不是 bug，是继承规则 —— **charset 继承库，collation 回落到 charset 固有默认**。

### 为什么必须现在修

排序规则决定了**字符串比较与排序的语义**。两张 collation 不同的表做字符串关联时，MySQL 无法决定采用谁家的规则，会直接报错：

```
Illegal mix of collations
(utf8mb4_general_ci,IMPLICIT) and (utf8mb4_0900_ai_ci,IMPLICIT)
for operation '='
```

现在只有一张表，所以**不影响运行**；但 **P1 就要加表**，届时必然踩到。现在改成本最低。

### 改法

**① 改库默认（元数据变更，不动任何数据，瞬间完成）**

```sql
ALTER DATABASE wx_push CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

表本来就是 `0900_ai_ci`，**表不需要动**。

**② 同步修 `schema.sql`，让全新部署一致**

```sql
CREATE DATABASE IF NOT EXISTS wx_push
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;        -- 改为 0900_ai_ci

CREATE TABLE IF NOT EXISTS wx_message_log (
    ...
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;        -- 显式补上，不再依赖继承
```

### 为什么选 `0900_ai_ci` 而不是反向对齐 `general_ci`

| 维度 | `utf8mb4_general_ci` | `utf8mb4_0900_ai_ci` |
|---|---|---|
| Unicode 版本 | 较旧，支持不完整 | Unicode 9.0 |
| 中文/emoji/多语言排序 | 部分字符顺序不正确 | 正确 |
| 大小写/重音折叠 | 简单规则 | 完整规则（ai = accent-insensitive，ci = case-insensitive） |
| 是否现代默认 | 历史兼容选项 | **MySQL 8.0+ 默认**，本机服务器默认 |
| 性能 | 略快（规则简单） | 现代版本已优化，差距可忽略 |

**结论**：统一到 `0900_ai_ci`。

### 验证方式

```sql
SELECT '库' AS 层级, DEFAULT_COLLATION_NAME AS 排序规则
  FROM information_schema.SCHEMATA WHERE SCHEMA_NAME='wx_push'
UNION ALL
SELECT '表', TABLE_COLLATION
  FROM information_schema.TABLES
 WHERE TABLE_SCHEMA='wx_push' AND TABLE_NAME='wx_message_log';
```

**期望**：两行都是 `utf8mb4_0900_ai_ci`。

## 题 3 · 唯一索引为什么挡不住事件消息的重复？

### 现象

`uk_msg_id` 唯一索引 + `INSERT IGNORE` 明明能挡住文本消息的重复，事件消息却挡不住。
实测**连跑两轮冒烟脚本**：`msg_id IS NULL` 的行数从 2 变成 4。

### 答案

**因为 `NULL` 在唯一索引里不参与冲突判定。**

- SQL 语义中 `NULL` 表示「未知」，所以 `NULL = NULL` 的结果是 `UNKNOWN`，**不是 `TRUE`**
- MySQL 严格遵循这个语义：**唯一索引允许多个 `NULL` 值共存**

于是两条路径分岔了：

| 消息 | `msg_id` 值 | 第二次插入时 | 结果 |
|---|---|---|---|
| 文本消息 | `'1234567890123456'` | 值相等 → **冲突** | 被 `IGNORE` 静默跳过 ✅ |
| 事件消息 | `NULL` | 每次都是「未知」→ **永不冲突** | 全部写入 ❌ |

**这个行为是有意设计的**（`schema.sql` 注释里写了），但它有个**真实代价**：

微信在超时或失败后会**重推**同一条消息。事件消息（关注/取关）被重推时会产生**重复流水**。将来 admin 用这张表统计「关注数 / 取关数」，数字会**偏高**。这是会直接污染后台数据准确性的问题。

### 改法：自己合成幂等键

**核心认知**：唯一键**不必来自微信** —— 只要能保证「**同一条消息被重推时，算出来的键完全相同**」即可。

对事件消息，用这几个稳定字段合成：

```
dedupKey = SHA-1( fromUserName + '|' + msgType + '|' + event + '|' + createTime )
```

**每个字段都有必要**：

| 字段 | 少了会怎样 |
|---|---|
| `fromUserName` | 不同用户在同一秒触发同种事件 → 被误判为同一条 |
| `msgType` | 事件与消息的类型空间混在一起，将来扩展易撞 |
| `event` | 关注与取关无法区分 |
| **`createTime`** | **最关键** —— 少了它，「关注 → 取关 → 再关注」三次会被误判成同一条 |

**实现细节**：

- 分隔符用 `|`：防止字段拼接歧义（`"ab" + "|c"` 与 `"a" + "b|c"` 会撞）
- 用 **SHA-1** 而非 `String.hashCode()`：后者碰撞率高，且规范不保证跨 JVM 一致
- 输出固定 40 字符十六进制，`VARCHAR(64)` 足够
- 必须**确定性**：绝不能用随机数或 `now()`

### 两个落地方案

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A · 复用 `msg_id` 列** | 事件消息时把合成哈希写进 `msg_id` | **零 schema 改动**，现有 `uk_msg_id` 直接生效 | 语义混浊：`msg_id` 既可能是微信 ID 又可能是哈希，与列注释矛盾 |
| **B · 新增 `dedup_key` 列** | 新增 `dedup_key VARCHAR(64) NOT NULL`，普通消息存 `MsgId`、事件存哈希；唯一索引建在它上 | 语义清晰、注释一致、可扩展 | 需改 DDL + 实体 + Mapper |

**推荐 B**，两个理由：

1. 这张表要长期支撑 admin 的统计查询，**字段语义清晰**比省一次 DDL 更值；
2. A 有隐藏风险 —— 真实微信事件的 `msg_id` **恒为 `NULL`**，一旦将来微信给事件也带上 `MsgId`，两套语义会互相打架，且没有列来区分。

### 方案 B 的具体改动

**① DDL**

```sql
ALTER TABLE wx_push.wx_message_log
    ADD COLUMN dedup_key VARCHAR(64) NOT NULL COMMENT '幂等键：普通消息用 MsgId，事件用合成哈希' AFTER msg_id,
    ADD UNIQUE KEY uk_dedup_key (dedup_key);

-- 旧数据回填（当前只有测试数据，可直接清空重来）
-- UPDATE wx_push.wx_message_log SET dedup_key = msg_id WHERE msg_id IS NOT NULL;
```

> ⚠️ 新增 `NOT NULL` 列会给已有行填默认值（空字符串），会让唯一索引立刻冲突。
> 当前表里只有 5 行测试数据，**最干净的做法是 `TRUNCATE` 后重建**，不需要回填。
> 这属于破坏性操作，**必须单独确认**。

**② 实体**：`WxMessageLog` 加 `dedupKey` 字段

**③ 幂等键计算**：建议放在 `WxMessageService` 或一个独立的 `DedupKeyGenerator`（单一职责）

```java
/** 计算幂等键：有 MsgId 直接用；没有（事件消息）则合成 */
public static String of(InboundMessage msg) {
    if (StringUtils.hasText(msg.getMsgId())) {
        return msg.getMsgId();
    }
    String raw = String.join("|",
            nullSafe(msg.getFromUserName()),
            nullSafe(msg.getMsgType() == null ? null : msg.getMsgType().code()),
            nullSafe(msg.getEvent()),
            msg.getCreateTime() == null ? "" : String.valueOf(msg.getCreateTime()));
    return sha1Hex(raw);
}
```

**④ Mapper XML**：`insertIgnore` 的列里加上 `dedup_key`，唯一冲突改由它承担

> `uk_msg_id` 可以保留（对真实消息仍是有效的约束），也可以删掉。**建议保留** —— 它是列级约束，不会冲突。

### ⚠️ 只影响入库，不影响回复

改动**只作用于 `persistQuietly()` 那一步**。重复事件仍然**照常返回回复**，这与现有的「重复消息不入库、但仍要回复」设计保持一致 —— 因为微信重推往往意味着上一次回复没送达，用户还在等。

### ✅ 最终实现（2026-09-22 落地）

以上是**设计期的建议稿**。落地时有三处调整 —— 保留原文，是为了对照「想到的」与「做成的」差在哪：

| 项 | 建议稿 | 最终实现 | 为什么改 |
|---|---|---|---|
| 列定义 | `VARCHAR(64) NOT NULL` | `VARCHAR(255) DEFAULT NULL` | `NOT NULL` 会给已有行填空串，**唯一索引立刻冲突**；允许 NULL 才能安全回填。255 是因为事件键最坏约 237 字符（`evt:` + openid 64 + event 32 + eventKey 128 + 时间戳 10 + 分隔符） |
| 事件键 | SHA-1 合成哈希 | **明文拼接** | 排查时一眼能看出是哪条事件。哈希只解决「太长」，而长度问题已被 `VARCHAR(255)` 解决 |
| `uk_msg_id` | 建议保留 | **降级为普通索引** | 保留它不增加价值，却让「到底哪个索引在保证幂等」变含糊。降级后**只剩一个唯一键**，语义唯一 |

还补了一条建议稿里没写的保护：**键超过 255 字符时返回 `null`（放弃去重），绝不截断** ——
截断会把两条不同的消息拼成同一个键，导致**真实消息被静默丢弃**；
而「消息丢了」比「消息重复」难发现得多，宁可不去重。

**落地位置**：`domain/DedupKey.java`（键规则）+ `db/alter-002-add-dedup-key.sql`（一次性迁移）。
检测步骤见 `docs/幂等修复-检测清单.md`（D1–D9）。
