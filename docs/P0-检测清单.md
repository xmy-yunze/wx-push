**实测结果（已完成 ✅）**：

| 指标 | 实测值 | 判定 |
|---|---|---|
| 总行数 | 5 | — |

| `msg_id IS NULL` 的行数 | 4 | 事件消息两轮各 2 条，`NULL` 不参与唯一性约束 |

## 六、我发现的两件事（需要你知道）

1. **本机 MySQL 端口是 3326，不是 3306**。已写进 `application.yml` 注释。`33060` 是 MySQL X Protocol（给 MySQL Shell / X DevAPI 用的），JDBC 连它会报协议不匹配。
2. **`.gitignore` 已就位**，`application-local.yml`、`*.key`、`.env` 都被排除 —— 你的 AppSecret 将来放环境变量或本地配置文件，不会误提交。
3. ⚠️ **库与表的 collation 不一致**（建表时实测发现）：**库**是 `utf8mb4_general_ci`，**表**却是 `utf8mb4_0900_ai_ci`。
   成因：`schema.sql` 里表级只写了 `DEFAULT CHARSET = utf8mb4` 而**没写 `COLLATE`**，于是表继承了 MySQL 9 的服务器默认排序规则，没跟随库的设置。

   **当前只有一张表，不影响运行**；但隐患在后面——将来建第二张表时，若某张继承库默认（`general_ci`），两表做字符串 `JOIN` 会直接报
   `Illegal mix of collations`。P1 要加表，建议先统一。

   > 推荐统一到 `utf8mb4_0900_ai_ci`（Unicode 排序更正确、性能更好），做法是在 `schema.sql` 的 `CREATE TABLE` 末尾显式补上
   > `COLLATE = utf8mb4_0900_ai_ci`，并同步改 `CREATE DATABASE` 那一行。**改法要动 DDL，等你确认。**

4. ⚠️ **事件消息没有幂等保护**：`msg_id` 为 `NULL` 的事件消息不参与唯一性约束，微信重推会**产生重复流水**（实测第二轮脚本又写了 2 条 `NULL` 行）。
   **当前不影响回复链路**，但将来 admin 若用这张表统计「关注/取关数」，重复会导致**统计偏高**。
   可选修法：为事件消息合成幂等键（如 `FromUserName + Event + CreateTime` 的哈希）另存一列并加唯一索引。
