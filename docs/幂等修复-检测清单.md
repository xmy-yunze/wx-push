# 幂等修复 · 检测清单（dedup_key）

> 制定时间：2026-09-22
> 对应改动：`docs/P0-遗留问题-改法问答.md` 遗留 #3（事件消息无幂等）
> 根因一句话：**事件消息没有 `MsgId` → `msg_id` 落成 `NULL` → MySQL 唯一索引不比较 `NULL` → `INSERT IGNORE` 形同失效**

---

## 🔴 执行顺序（违反会导致「消息一条都不进库」）

**必须先执行数据库迁移，再启动后端。**

理由说得具体一点：代码已经改成往 `dedup_key` 列写值。如果数据库里还没有这一列，
`insertIgnore` 会抛 `Unknown column 'dedup_key' in 'field list'`，而这个异常被
`WxMessageService#persistQuietly` 的 `try/catch` **兜住了**（设计如此，落库失败不影响回复）——
于是现象是：

```
后端启动正常、接口全部 200、回复正常、日志里只有一行 warn
→ 但消息记录页空空如也
```

**这是最隐蔽的一类故障**：主链路一切正常，只有辅助能力静默失效。所以顺序不能颠倒。

## 一、改了什么

| 层 | 文件 | 变更 |
|---|---|---|
| DDL | `backend/src/main/resources/db/alter-002-add-dedup-key.sql` | **新增**：给 `wx_message_log` 加 `dedup_key` 列并建唯一索引（一次性迁移） |
| DDL | `backend/src/main/resources/db/schema.sql` | 建表语句同步：`dedup_key VARCHAR(255)` + `UNIQUE KEY uk_dedup_key`，`uk_msg_id` 降级为普通索引 `idx_msg_id` |
| 代码 | `domain/DedupKey.java` | **新增**：去重键计算（普通消息 `msg:<MsgId>`；事件 `evt:<FromUser>:<Event>:<EventKey>:<CreateTime>`） |
| 代码 | `repository/entity/WxMessageLog.java` | 加 `dedupKey` 字段 |
| 代码 | `service/WxMessageService.java` | 落库时填充 `dedupKey` |
| 代码 | `repository/mapper/WxMessageLogMapper.java` + `mapper/WxMessageLogMapper.xml` | `insertIgnore` 改写入 `dedup_key`；resultMap / 列清单同步 |
| 测试 | `test/.../domain/DedupKeyTest.java` | **新增 16 个用例** |

### 两个刻意的选择（与这份文档早先的「建议稿」不同，理由如下）

| 项 | 建议稿 | 最终实现 | 为什么改 |
|---|---|---|---|
| 列定义 | `VARCHAR(64) NOT NULL` | `VARCHAR(255) DEFAULT NULL` | `NOT NULL` 给历史行填默认空串会**立刻让唯一索引冲突**；允许 NULL 才能安全回填。长度 255 是因为事件键最坏情况约 237 字符（`evt:` + openid 64 + event 32 + eventKey 128 + 时间戳 10 + 分隔符） |
| 事件键 | SHA-1 合成哈希 | **明文拼接** `evt:a:b:c:d` | 排查时能一眼看出是哪条事件；可读性换掉几十字节的存储，对个人号量级完全划算。哈希只解决"太长"，而长度问题用 `VARCHAR(255)` 就解决了 |
| `uk_msg_id` | 建议保留 | **降级为普通索引** | 保留唯一约束没有额外价值（`msg_id` 在普通消息里本就唯一），却让"到底哪个索引在保证幂等"变得含糊。降级后**只有一个唯一键**，语义唯一 |

### 长度保护：超长时返回 `null`，绝不截断

`DedupKey.of()` 超过 255 字符会返回 `null`（= 放弃去重，记录照写）。
**截断是更糟的选择**：它会把两条不同的消息拼成同一个键，导致**真实消息被静默丢弃** ——
"消息丢了"比"消息重复"难发现得多，宁可不去重。

### D6 · 🎯 核心：事件消息幂等（修复前后对比）

**原理**：冒烟脚本里所有事件的 `CreateTime` 都是固定值，所以**连跑两轮就等于模拟微信重推**。

```bash
# 连跑两轮
./backend/scripts/smoke-test.sh 你的真实Token 18080
./backend/scripts/smoke-test.sh 你的真实Token 18080

# 查有没有重复的去重键
mysql -h127.0.0.1 -P3326 -uroot -p -e "
SELECT dedup_key, COUNT(*) AS 次数
FROM wx_push.wx_message_log
WHERE msg_type = 'event'
GROUP BY dedup_key
HAVING COUNT(*) > 1;"
```

**期望**：**`SELECT` 返回 0 行**（Empty set）。

| | 改前（实测） | 改后（期望） |
|---|---|---|
| 两轮冒烟后，事件的重复 `dedup_key` | **有重复**（同一 CLICK 写了两行，时间戳 `20:44:07.267` / `.280`） | **0 行重复** |

### D7 · 真实重复动作不能被误挡

修复不能矫枉过正 —— 用户**真的**点了两次同一个菜单，应该是两条记录。

```bash
# 手工发两条 EventKey 相同、但 CreateTime 不同的事件
cd ~/Desktop/微信公众号/wx-push
TOKEN=你的真实Token
send() {
  TS=$1; NONCE=$2; CT=$3
  SIG=$(printf '%s\n' "$TOKEN" "$TS" "$NONCE" | LC_ALL=C sort | tr -d '\n' | shasum -a 1 | cut -d' ' -f1)
  curl -s -m 5 -X POST "http://127.0.0.1:18080/wx?signature=${SIG}&timestamp=${TS}&nonce=${NONCE}" \
    -H "Content-Type: text/xml" -d "<xml><ToUserName><![CDATA[gh_abc]]></ToUserName><FromUserName><![CDATA[oUserX]]></FromUserName><CreateTime>${CT}</CreateTime><MsgType><![CDATA[event]]></MsgType><Event><![CDATA[CLICK]]></Event><EventKey><![CDATA[MENU_ABOUT]]></EventKey></xml>" > /dev/null
}
send 1700000201 n1 1700000201
send 1700000202 n2 1700000202

mysql -h127.0.0.1 -P3326 -uroot -p -e "
SELECT dedup_key, COUNT(*) AS 次数 FROM wx_push.wx_message_log
WHERE from_user = 'oUserX' GROUP BY dedup_key;"
```

**期望**：`oUserX` 名下 **2 行**（两个不同 `CreateTime` → 两个不同键）→ 证明不会误挡真实行为。

## 三、回滚

```sql
ALTER TABLE wx_message_log DROP INDEX uk_dedup_key, DROP COLUMN dedup_key;
ALTER TABLE wx_message_log DROP INDEX idx_msg_id, ADD UNIQUE KEY uk_msg_id (msg_id);
```

> 回滚后会重新暴露出「事件消息重复入库」的问题。**回滚前必须同时把代码也退回去**，
> 否则 `insertIgnore` 会因缺列而失败（表现同 §🔴）。
